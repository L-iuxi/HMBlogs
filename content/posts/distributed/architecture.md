# 数据系统架构中的权衡

如果数据管理是开发的时候要面临的主要挑战，我们称这种应用为**数据密集型**应用。计算密集型应用关心怎么把庞大的计算并行化，而对于数据密集型应用，我们关心怎么存储和处理海量数据，怎么管理数据变更，怎么在故障和并发面前保证一致性，如何维持高可用。
本章的内容是了解几种不同的做法，各有利弊，以及一些专业的术语，对分布式数据系统建立基本的认识。

## 分析型与事务型系统
事务型系统（operational system）由创建数据的后端服务和数据基础设施组成，例如直接为外部用户提供服务。应用代码根据用户执行的操作，读取和修改数据库中的数据。

分析型系统（analytical system）服务于业务分析师和数据科学家。它们保存事务型系统数据的只读副本，并针对分析所需的数据处理方式进行优化。

事务型系统通常按某个键进行少量查询，也就是点查询，以及一些查改操作。由于这些操作具有交互性，这种访问模式称为**联机事务处理（OLTP）**。
分析型系统通常按某个键进行大量查询，也就是批量查询，以及一些查改操作。由于这些操作具有批量性，这种访问模式称为**联机分析处理（OLAP）**。

## 数据仓库
一套数据同时用于事务处理和分析查询，可能产生一些问题，譬如数据孤岛（data silo），性能影响等。
相比之下数据仓库是一个独立的数据库，分分析师可以查询而不影响 OLTP 的运行。这些仓库往往保存 OLTP 的只读副本。数据先从 OLTP 中抽取出来，再载入数据仓库，这个过程称为**ETL：提取—转换—加载**。有时也会对调**转换**和**加载**的顺序，也就是**ELT**。
有些数据库会提供**HTAP混合事务/分析处理**，但是这样可能需要业务分析师协调多个数据库，所以 HTAP 并不能取代数据仓库。

## 数据湖
数据科学家需要吧数据转换成适合机器学习的模型，其中的数值称为特征，或者对文本数据进行分析提出结构化的信息。这个时候引入数据湖这个概念。
数据湖——一个集中的数据存储库，保存一切对分析有用的副本无论文件格式或者数据模型，这些数据通过 ETL 流程从事务型系统获得。数据湖更灵活而且比关系存储更便宜。

ETL 流程泛化为数据管道，数据湖往往成为前往数据仓库中的一站，数据湖用事务型系统产生的原始形态保存数据，每个数据消费者都可以把数据转换成自己需要的形式。而也可以在数据湖上建立执行查询和原数据层，Apache Hive、Spark SQL、Presto 和 Trino 都采用了这种方法。

## 记录系统与衍生数据系统

**记录系统**也称权威数据源（source of truth），保存某类数据的权威或 规范（canonical）版本。新数据到来时，例如用户输入，首先写入这里。每项事实只表示一次，通常采用 规范化（normalized）表示（参见“规范化、反规范化与连接”）。如果其他系统与记录系统的数据不一致，那么按照定义，应以记录系统中的值为准。

**衍生系统**中的数据，是以另一个系统中的现有数据为基础，经过某种转换或处理而得到的结果。衍生数据即使丢失，也可以从原始数据源重新创建。缓存就是一个典型例子：若数据在缓存中，便可直接返回；若缓存中没有所需数据，则可以退回底层数据库读取。反规范化值、索引、物化视图、转换后的数据表示，以及在数据集上训练的模型，也都属于这一类。
## 云服务
**云原生**一词用来描述专门利用云服务优势而设计的架构，从一开始就按照云原生思路设计的系统已经展现出若干优势：在相同硬件上性能更好，故障恢复更快，支持更大的数据集等
下面是一个 Google Cloud Spanner 的例子
> Google Cloud Spanner从设计之初就是一个分布式数据库，它的核心目标是让数据能够分布在全球多个数据中心，同时依然支持关系型数据库的SQL，事务和强一致性。
> Google Cloud Spanner的分布式设计主要来源于以下几个方面
> 1. 数据分片成多个Split，每个Slite存储一部分数据并分布在不同的服务器上。与此同时，Spanner会给数据维护多个副本，这一部分使用基于 paxos 的复制机制，让多个副本对数据更新达成一致。
> 2. 跨地域部署，可以把数据库部署在不同的地理区域，数据更新需要通过一致性协议进行协调
> 3. Spanner 通过 2PC 协调跨分片事务，对于在不同分片上的两个操作，保证要么全部成功要么全部失败，内部副本分片的一致性通过 Paxos 保证
> 4. 在分布式系统中，不同机器的时间可能有时差，只依赖机器的本地时间，很难判断不同事务的顺序，SPanner 通过 TrueTime API提供带有不确定性区间的时间信息，并且通过 Commit Wait机制保证时间戳的外部一致性

## 存储计算分离
在传统计算中，磁盘存储被视为持久存储。为了容忍单块硬盘故障，人们通常使用 **RAID（独立磁盘冗余阵列**，云中的计算实例也可以连接本地磁盘，但为了防止本地磁盘无法访问的故障，云服务提供虚拟磁盘存储，把磁盘I/O转换为了网络调用，模拟磁盘的行为。
> RAID（Redundant Array of Independent Disks），中文叫独立磁盘冗余阵列。通过将多个硬盘组合起来，提高磁盘的读写性能，数据可靠性。常见的方式有：
> 1. RAID 0：条带化，将数据分块存储在多个磁盘上，提高读写性能，但无数据可靠性。
> 2. RAID 1：镜像，将数据复制到多个磁盘上，提高数据可靠性，但读写性能较慢。
> 3. RAID 5：分布式奇偶校验，数据和校验信息分布在多块磁盘上。
> 4. RAID 6：分布式奇偶校验，数据分块存储在多个磁盘上，校验信息分布在多块磁盘上。

## 分布式和单节点系统
由多台机器通过网络通信而构成的系统，称为分布式系统，参与分布式系统的每个进程称为一个节点。
分布式系统有优点也有缺点，每一个经过网络的调用都有可能失败，比如网络中断，请求超时。这时候我们不能简单的判定结果是成功或者失败，重试也未变安全。而且分布式系统并非更快，参考redis。
分布式系统往往很难排查故障，用于诊断分布式系统的问题的技术称为可观测性，他执行系统数据，允许人们调用查询。此外，还要保证数据一致性，分布式事务的问题。

## 微服务
把系统分布到多台机器上，最常见的做法是将它划分为客户端和服务器，由客户端向服务器发送请求。这种通信最常使用 HTTP，我们将在“流经服务的数据流：REST 与 RPC”中进一步讨论。同一个进程既可以是服务器（处理传入的请求），也可以是客户端（向其他服务发出请求）。

这种构建应用的方式传统上称为 面向服务架构（SOA）；近年来，这一思想又进一步演化为 微服务（microservices）架构 52 53。在这种架构中，每项服务都有明确的用途（例如 S3 的用途就是文件存储）；服务通过 API 向客户端开放能力，由客户端经网络调用；每项服务还由一个团队负责维护。这样一来，复杂应用就可以拆分成多项相互交互的服务，分别由不同团队管理。

无服务器（serverless），又称 函数即服务（FaaS），是另一种服务部署方式：它把基础设施管理进一步外包给云服务商 33。使用虚拟机时，你必须明确决定何时启动或关闭实例；无服务器模型则由云服务商根据发往服务的请求，自动分配和释放硬件资源 54。这种部署方式把更多运维负担转移给云服务商，并允许按使用量灵活计费，不再按机器实例收费。为了提供这些好处，许多无服务器基础设施会限制函数执行时长和运行时环境，而且函数第一次调用时可能启动缓慢。“无服务器”这个名称也容易误导：每次执行无服务器函数仍然要用到一台服务器，只是下一次执行可能换到另一台。此外，BigQuery 和各种 Kafka 产品也采用了“无服务器”这个说法，用来表示服务能够自动伸缩，并按使用量而不是机器实例收费。
