# 关系模型和文档模型
在关系模型中，数据被组织成关系，每个关系都是由元组构成的无序集合。常见的比如RDBMS，SQL。SQL 在关系模型这个核心上不断吸收其他数据类型，增加了对 XML 和 JSON 的支持。之后NoSQL迅速发展，NoSQL是围绕新数据模型，模式灵活性，可伸缩性和开源模式形成的宽泛理念。而以 JSON 表示数据的文档模型也广受欢迎，比如 MongoDB。
文档数据和关系数据有几个常见的问题

## 对象关系不匹配
### ORM
数据如果要存储在SQL这种关系表中，就需要一个笨拙的转换层，可以通过**对象关系映射ORM**解决，常见的比如GORM。
但是 ORM 很容易在无意中写出低效查询，比如 N+1 查询。
> 假设你要在页面上显示用户评论列表：先用一条查询取回 N 条评论，每条都含有作者 ID；为了显示作者姓名，还要用这个 ID 查询用户表。手写 SQL 时，你大概会直接在查询中连接用户表，让每条评论连同作者姓名一起返回；使用 ORM 时，却可能对 N 条评论逐条查询用户表，最终一共执行 N+1 条数据库查询。
此外，ORM一般只用于 OLTP 应用。

### 一对多关系的文档数据模型
大部分人的职业生涯都不止有一份工作，联系方式也可能有多向。这些一对多关系，可以把职位，教育经历，联系方式单独放在表中，再通过外键引用user表。或者表示为JSON文档。
在关系模型中，取回一份个人资料，需要进行多次查询或者在表之间建立繁琐的链接。在JSON表示中，所有相关信息都集中在一处，形成类似的树状结构。

## 规范化和反规范化
在一个字段中，比如 address，不使用字符串，而是采用 id 表示。这样就是**规范化**，使用ID的时候数据更加规范化，对人有意义的信息只存储一份，其他地方都用只在数据库内有意义的ID来引用他。若直接存储文本，这段信息就会复制到每条使用它的记录中，这样的表示是**反规范化**的。
但是规范化在每次查找的时候都要多做一次查找，做id到字符串的映射。通常来说，规范化数据写入快，查询慢，反规范化数据读取快，写入代价高。除此之外，还要考虑进程在更新中途崩溃的时候，数据库能否保持一致性，为跨多个文档的操作提供原子性。

## 多对多
在关系模型中的多对多关系，比如一个人曾任职多个工作，一个公司有多个员工，这类关系通常用关联表（连接表）表示，每个职位把一个用户ID和一个组织ID关联。在文档模型中，多对多关系很难塞进一个文档，最好使用规范化表示，一组文档指向对其他文档的引用。
除此之外，也可以通过类似倒排索引的方式，同时建立两边的映射关系，或者二级索引的方式。

## 星型和雪花型模型
数据仓库通常采用关系模型，其表结构有几种广泛使用的惯例：星型模式（star schema）、雪花模式（snowflake schema）、维度建模（dimensional modeling），以及 一张大表（one big table，OBT）

### 星型模式
星型模式源于表关系的可视化形状，事实表位于中央，周围环绕着维度表，链接这些表的线条就像是星星。
> 事实表的每一行表示在特定事件发生的事件，比如对于一个网站，每一行可能是一次页面浏览或者一次用户点击
> 维度表是事实表中的列指向其他表的外键引用，事实表的一行表示一个时间，各个维度则表示事件发生的对象内容，地点等
![数据模型](ddia-data-1.png)

### 雪花模式
这个模版的变体是雪花模式，其中的维度会进一步分解为子维度。雪花模式比星型模式更规范化。

### 一张大表
完全省去维度表，把维度信息放进事实表的反规范化列中。称为一张大表，虽然占用更多空间，但是让查询更快

# 图数据模型
如果多对多关系在数据中十分常见，那么将数据建模为图更自然。图由节点和边组成。
图可以用几种不同的方式表示，在邻接表模型中，每个顶点都保存与它相隔一条边的相邻顶点ID，或者邻接矩阵，这是一个二维数组，每行每列对应一个顶点。邻接表适合图遍历，邻接矩阵适合机器学习。
图还有一项同样强大的用处，用一致的方式在单个数据库中存储截然不同的对象。

## 属性图
在属性图模型中每个顶点包括：
- 唯一标识符
- 一个标签（字符串），描述该顶点所表示的对象类型
- 一组出边
- 一组入边
- 一组属性（键值对）
每条边包括：
- 唯一标识符
- 边的起点（尾部顶点，即 tail vertex）
- 边的终点（头部顶点，即 head vertex）
- 一个标签，描述两个顶点之间的关系类型
- 一组属性（键值对）
可以把图存储看成两个关系表，一张存储顶点，一张存储边。
这个模型有几个重要特点：
1. 任何顶点都可以通过边连接到任何其他顶点。没有模式限制哪些可以关联哪些不可以。
2. 给定任何顶点，都能高效的找到他的出边和入边，从而双向遍历图。
3. 为不同类型的顶点和关系使用不同的标签，可以在一张图中存储多种不同的信息

# 事件溯源
在以上数据模型中，数据都以写入时的形式接受查询，无论他是 JSON 文档还是行，在复杂情况中，我们需要找到一种数据表示，能够满足所有查询和展示数据的需求。我们可以用一种形式写入，再从中派生出多种针对不同读取方式的优化。
比如说写入数据日志，新的日志追加到旧的后面，日志中的事件是不可变的，只会向日志追加更多事件。
以事件作为权威数据源，把每次状态变化都表达为事件，这种思路称为**事件溯源**。
维护独立的读取优化表示，并且从写入优化的表示中派生它们，这种原则称为**命令查询责任分离**。
