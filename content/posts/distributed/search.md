设计数据密集型应用——搜索和查询
<!--more-->
本章会讨论，数据库如何存储我们提供的数据，以及如何在我们需要的时候重新找到数据。也就是存储引擎和查询。
为了高效查找数据库中特定的值，我们需要一种数据结构：索引。索引的大致思想是以某种特定的方式组织数据，从而更快的定位想要的数据，如果想要用多种不同的方式搜索同一份数据，那么需要在数据的不同部分建立多个索引
索引的存在可以加快读查询，但是索引会占用额外的磁盘空间，而且会拖慢写入速度。

# 哈希
如果只是为了加快数据的读取速度，可以为每个数据保留一个内存中的 **hash** 映射，记录数据在文件中的偏移量，指明键的最新值在何处。追加新的键值对的时候更新哈希映射。这种方式很快，但存在几个问题。
- 哈希映射没有持久化，数据库重启就需要重建，如果数据量很大，重启就会很缓慢
- 被新值覆盖的旧条目可能会仍然占着磁盘空间。
- 哈希表需要大量随机访问I/O，并且扩容成本很高，需要解决哈希冲突
- 范围查询效率不高

# SSTable（LSM）
**SSTable**（Sorted String Table）排序字符串表，这是一种按照key排序，写入后不可修改的键值存储文件。把数据保存在按键排序的结构中。这种文件格式保证键值对按键排序，而且每个键在文件中只出现一次。
这样就可以不在内存中保存所有键，把SSTable中的键值对分成若干个几千字节大小的块，索引只存每个块第一个键，这种只收录部分键的索引称为**稀疏索引**。索引存在 SSTable 中的一个独立区域中，采用不可变B树，字典树等可以快速查询的数据结构。查询的时候先通过索引找到对应的Block，再读取查找数据。
每个记录块都可以压缩，可以节省磁盘空间，减少 I/O 带宽的使用，代价是多耗费一点 CPU 时间。SSTable 比追加日志更便于读取，但是让写入变得十分困难，如果直接追加会让文件不再有序，如果每次都重写SSTable成本太高。采用**日志结构**方法，把仅追加日志和排序文件结合起来，也就是**LSM-Tree（Log-Structured Merge-Tree，日志结构合并树）**：
1. 收到写入的时候将其加入内存中的有序映射数据结构，例如红黑树，跳表或者字典树。这类数据结构可以按任意数据插入键，高效寻找键，按顺序读出键，这个内存数据结构称为内存表（memtable）。
2. 当内存表超过某个阈值的时候，按排序顺序把它写成磁盘上的 SSTable文件，这个文件称为数据库最新的 Segment，和旧的段在独立文件中，每个段都有自己的索引。向磁盘写段的时候，数据库可以向新的内存表写入，SSTable写完之后旧内存表可以释放。
3. 读取某个键的时候，先在内存表和磁盘中最新的段查找，如果没有，就依次看更旧的段，如果任何段中都没有这个键，那么他不存在与数据库。
4. 后台不时运行合并和压缩过程。
> memtable 是内存中的有序数据结构，SSTable是磁盘上的有序不可变文件，Segment是一段独立的磁盘存储文件
如果要删除一个键，必须追加 tombstone 的删除记录。
段文件不可变让崩溃恢复变得简单，如果写出内存表或者合并段的时候发生崩溃，数据库只需要删除未完成的SSTable，再重新开始。用于持久化内存表写入的日志，可能因为写入一半崩溃留下不完整记录，可以通过日志中的校验和检测丢弃这些记录。
## 布隆过滤器 BLoom Filter
BLoom Filter是一个判断元素是否可能存在于集合中的数据结构，主要由一个位函数和多个hash函数组成。Bloom Filter可以解决查询数据的时候，检查多个 SSTable，造成产生多个磁盘I/O的问题。
如果查询时有任意一个对应位为 0，就能确定元素不存在；如果全部为 1，则只能说明可能存在，需要进一步查询。它允许一定的误判，但不会产生假阴性。

## compation
LSM存储的重要过程压缩，常见的选择有：
- 按大小分层压实：
  把新，小的SSTable合并到旧，大的SStable中，可以应对很高的写入吞吐，但是旧的SSTable会很大，合并的时候需要大量临时磁盘空间。
- 分级压实：
  把键范围拆分到小的SSTable中，把旧的数据移入不同的层级，这样可以增量的进行压实，所需磁盘空间也更小，分级压实的读取效率更高，因为存储引擎只需要检查较少的SSTable，就可以判断有没有需要的键

# 嵌入式数据库
RocksDB，SQlite这样的嵌入式数据库并不提供网络API，它们和应用代码运行在同一个进程中，读写本地磁盘上的文件，通过普通函数调用交互。
在数据小，并发事务少的情况下，嵌入式数据库是合适的选择。

# B tree
包含 N 个键的 B tree 深度是 O(logN)，大多数数据库只需要三四层深的B树。
B tree最基本的写操作是新数据覆盖磁盘上的页，覆盖并不会改变页的位置，覆盖写后，指向页的引用依然有效。（相比较 LSM tree只追加写）
一次覆盖写多个页很危险，如果数据库写完一部分就崩溃，出现不属于任何父页的孤儿页，如果硬件没有写入整页，称为页撕裂。为了数据库从崩溃中恢复，B tree一般采用预写日志(write-ahead log，WAL),这是一个追加写文件，对B tree的修改都必须先写入WAL，才能应用到树本身的页上。
一些数据库（如 LMDB）不覆写页，也不靠 WAL 进行崩溃恢复，而是采用写时复制（copy-on-write）方案 26。修改过的页写入新的位置，并为树中的父页创建新版本，使其指向新位置。这种方法对并发控制也很有用，我们将在 “快照隔离与可重复读” 中看到。

## 写放大
把某个工作负载实际写入磁盘的总字节数，除以不带索引、只写仅追加日志时所需的字节数，得到的比值就是**写放大（write amplification）。**
对 LSM tree 来说，一个值先写入日志保证持久性一次，内存表写入磁盘一次，此后每次compation再写入一次。
B tree 一次预写日志，一次写入树页本身。，相比较来说，LSM tree 的写放大更低。
在写入密集型应用中，瓶颈可能是数据库向磁盘写入的速度，写放大越高，在有限磁盘带宽里面处理的写入就越少。

# 全内存存储
最常见的 Redis，通过异步写入磁盘提供弱持久性。内存数据库的性能优势并不来自于省去了内存读取。内存数据库可能更快是因为省去了把内存数据结构编码成可以写入磁盘的形式的开销。
除了性能意外，内存数据库还可以提供很难用磁盘索引实现的数据模型。
