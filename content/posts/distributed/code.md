设计数据密集型应用——编码和演化
<!--more-->

当数据格式或者模式发生变化的时候。通常也需要相应的修改应用程序代码。但是在大型应用程序中，代码变更往往无法瞬间完成，对于服务端应用程序，可能需要执行滚动升级，每次先把新版本部署到少数几个节点，确认运行正常之后，再逐步部署到所有节点。这样无需中断服务就可以上线新版本。
新旧版本的代码以及新旧数据格式，可能同时存在于系统中，系统要继续顺利运行，就需要保持双向兼容。
向前兼容：旧的代码可以读取新代码写入的数据
向后兼容：新代码可以读取旧代码写入的数据

本章将介绍几种数据编码格式，Json，XML，Protocol Buffer等。


# 编码数据的格式
程序通常至少使用两种新式的数据，在内存中，数据保存在对象，结构体，列表，数组，哈希表，树等数据结构中。这些结构常使用指针，针对 CPU 的高效访问和操作进行了优化。
如果要将数据写入文件或者通过网络发送，就必须将其编码成某种自包含的的字节序列。因此也需要在两种表示之间进行转换。
也有一些情况不需要编码和解码，例如数据库直接操作从磁盘加载的压缩数据，还有一些零拷贝数据格式，无需显式的转换。
下面介绍一下简单的数据和编码格式。

##  特定语言的内置
许多编程语言都内置了将内存对象编码成字节序列的功能，这些编码库虽然方便，但是存在安全，兼容，低效率的问题。在数据做非常短暂使用的情况下可以考虑。

## JSON，XML
JSON、XML 和 CSV 都是文本格式，因而具有一定的人类可读性，可由多种编程语言读写，但是这些方式有一些不易察觉的麻烦：
- 数字的编码模糊，XML和CSV无法区分数值和数字字符串，JSON不分整数和浮点数。处理大数的的时候也会造成问题。
- JSON和XML不支持二进制字符串，人们把二进制字符串数据用base64编码成文本来绕过这一段限制，再说明应该用base64解析，体积约增加33%。

### JSON
JSON 模式可以采用开放或封闭的内容模型。开放内容模型允许出现模式未定义的任意字段，而且这些字段可以是任意数据类型；封闭内容模型则只允许出现显式定义的字段。在 JSON 模式中，把 additionalProperties 设为 true 就会启用开放内容模型，而这恰好是默认值。因此，JSON 模式通常是在定义 不允许什么（也就是已定义字段上的无效值），而不是穷举模式中允许什么。
除了开放和封闭内容模型以及验证器，JSON 模式还支持条件式 if/else 模式逻辑、命名类型、远程模式引用等诸多功能。这些能力造就了一门十分强大的模式语言，却也让模式定义变得庞杂难用。解析远程模式、推断条件规则，或者以向前或向后兼容的方式演化模式，都可能很有挑战 。XML 模式也有类似的问题。

### 二进制编码
JSON和XML于二进制相比来说很占空间，所以人们开发出了大量的JSON的二进制编码，其中一些格式扩展了数据类型集合，或者支持二进制字符串。

## Protocol Buffer
Protocol Buffer是 Google 开发的二进制编码库，Protocol Buffer要求任何待编码的数据都有模式，然后按照上述模式的定义生成用各种编程语言实现该模式的类，应用程序可以调用生成的代码来编码或者解码符合模式的记录。
Protocol buffer比JSON字节数少，很大一部分原因是因为它采用二进制编码，并且采用字段编号而不是字段名称。除此以外，Protocol buffer把字段类型和标签号塞进同一个字节，进一步节省空间，用每个字节的最高位表示后面是否还有更多字节，数字越大，占用的字节就越多。
在向前兼容中，向模式中添加新字段，只要给他分配一个新的标签号。虽然旧代码不知道新的标签号，遇到新代码写入的数据中无法识别的字段的时候只需要忽略该字段，借助数据类型，解析器知道需要跳过多少字节，同时应该保留未知字段。

## Avro
Apache Avro 是另一种二进制编码格式，作为 hadoop 的子项目。Avro 也使用模式来规定待编码数据的结构，他有两种模式语言，一种是供人编辑的 Avro IDL，，另一种基于JSON，更便于机器读取。
