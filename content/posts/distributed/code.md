设计数据密集型应用——编码和演化
<!--more-->

当数据格式或者模式发生变化的时候。通常也需要相应的修改应用程序代码。但是在大型应用程序中，代码变更往往无法瞬间完成，对于服务端应用程序，可能需要执行滚动升级，每次先把新版本部署到少数几个节点，确认运行正常之后，再逐步部署到所有节点。这样无需中断服务就可以上线新版本。
新旧版本的代码以及新旧数据格式，可能同时存在于系统中，系统要继续顺利运行，就需要保持双向兼容。
向前兼容：旧的代码可以读取新代码写入的数据
向后兼容：新代码可以读取旧代码写入的数据

本章将介绍几种数据编码格式，Json，XML，Protocol Buffer等。


# 编码数据的格式
程序通常至少使用两种新式的数据，在内存中，数据保存在对象，结构体，列表，数组，哈希表，树等数据结构中。这些结构常使用指针，针对 CPU 的高效访问和操作进行了优化。
如果要将数据写入文件或者通过网络发送，就必须将其编码成某种自包含的的字节序列。因此也需要在两种表示之间进行转换。
也有一些情况不需要编码和解码，例如数据库直接操作从磁盘加载的压缩数据，还有一些零拷贝数据格式，无需显式的转换。
下面介绍一下简单的数据和编码格式。

##  特定语言的内置
许多编程语言都内置了将内存对象编码成字节序列的功能，这些编码库虽然方便，但是存在安全，兼容，低效率的问题。在数据做非常短暂使用的情况下可以考虑。

## JSON，XML
JSON、XML 和 CSV 都是文本格式，因而具有一定的人类可读性，可由多种编程语言读写，但是这些方式有一些不易察觉的麻烦：
- 数字的编码模糊，XML和CSV无法区分数值和数字字符串，JSON不分整数和浮点数。处理大数的的时候也会造成问题。
- JSON和XML不支持二进制字符串，人们把二进制字符串数据用base64编码成文本来绕过这一段限制，再说明应该用base64解析，体积约增加33%。

### JSON
JSON 模式可以采用开放或封闭的内容模型。开放内容模型允许出现模式未定义的任意字段，而且这些字段可以是任意数据类型；封闭内容模型则只允许出现显式定义的字段。在 JSON 模式中，把 additionalProperties 设为 true 就会启用开放内容模型，而这恰好是默认值。因此，JSON 模式通常是在定义 不允许什么（也就是已定义字段上的无效值），而不是穷举模式中允许什么。
除了开放和封闭内容模型以及验证器，JSON 模式还支持条件式 if/else 模式逻辑、命名类型、远程模式引用等诸多功能。这些能力造就了一门十分强大的模式语言，却也让模式定义变得庞杂难用。解析远程模式、推断条件规则，或者以向前或向后兼容的方式演化模式，都可能很有挑战 。XML 模式也有类似的问题。

### 二进制编码
**JSON和XML**于二进制相比来说很占空间，所以人们开发出了大量的JSON的二进制编码，其中一些格式扩展了数据类型集合，或者支持二进制字符串。

## Protocol Buffer
**Protocol Buffer**是 Google 开发的二进制编码库，Protocol Buffer要求任何待编码的数据都有模式，然后按照上述模式的定义生成用各种编程语言实现该模式的类，应用程序可以调用生成的代码来编码或者解码符合模式的记录。
Protocol buffer比JSON字节数少，很大一部分原因是因为它采用二进制编码，并且采用字段编号而不是字段名称。除此以外，Protocol buffer把字段类型和标签号塞进同一个字节，进一步节省空间，用每个字节的最高位表示后面是否还有更多字节，数字越大，占用的字节就越多。
在向前兼容中，向模式中添加新字段，只要给他分配一个新的标签号。虽然旧代码不知道新的标签号，遇到新代码写入的数据中无法识别的字段的时候只需要忽略该字段，借助数据类型，解析器知道需要跳过多少字节，同时应该保留未知字段。

## Avro
**Apache Avro**是另一种二进制编码格式，作为 hadoop 的子项目。Avro 也使用模式来规定待编码数据的结构，他有两种模式语言，一种是供人编辑的 Avro IDL，，另一种基于JSON，更便于机器读取。
> Hadoop 是一个开源的分布式大数据处理框架，主要用于解决海量数据分布式存储和计算问题，他的核心思想是把大数据拆分到多个机器上，再将结果汇总。其核心组件包括 HDFS(分布式文件系统) 和 YARN(资源管理系统) 以及 MapReduce(分布式计算模型)。

Avro 的编码模式中没有标签号，是现在所见编码中最紧凑的，编码仅是各个值的拼接，字符串就是长度+UTF-8字节，整数使用变长编码

> **变长编码（Variable-Length Encoding）**就是根据数据本身的大小或出现频率，使用不同长度的二进制位来表示数据，而不是所有数据都使用固定长度。
要解析二进制数据，必须按照字段在模式中出现的顺序逐一读取，并由模式告知每个字段的数据类型，这意味着，读取数据的代码只有使用与写入代码完全相同的模式才能正确解码二进制数据。

### 写入者模式与读取者模式
当应用程序要解码数据，例如写入文件或者数据库，或者通过网络发送，他会使用自己已知版本的模式，这就是**写入者模式**。
当应用程序要解码程序，例如从文件或者数据库读取，或者从网络接受，他会使用两个模式，一个是与写入时完全相同的写入者模式，另一个是可能有点不同的**读取者模式**。
如果读写双方模式相同，解码很简单，否则，Avro会比较写入者模式和读取者模式，把数据从前者转换成后者。取代码如果遇到只存在于写入者模式、却不在读取者模式中的字段，就将其忽略；如果读取代码需要某个字段，而写入者模式中没有同名字段，就填入读取者模式声明的默认值。
为了保持兼容，只能添加或者删除带默认值的字段。

> 什么是写入者模式？这个问题取决于 Avro 的使用场景

> 包含大量记录的大文件，这种情况下所有记录都使用同一个模式编码，文件写入者只需要在开头写入一次写入者模式即可。

> 逐条写入记录的数据库，可以在每条编码记录的开头放一个版本号，在数据库中维护模式版本列表。读取者取出记录之后先提取版本号，再从数据取得该版本对应的写入者模式解码。例如 Apache Kafka。

> 通过网络连接发送记录，当两个进程通过双向网络连接通信的时候，可以在建立连接的时候协商模式版本，并且连接的整个生命周期使用这个模式。
Avro对动态生成的模式很友好。

# 数据流的格式
数据由一个进程流向另一个进程，下面讨论常见的进程间数据流

## 数据库的数据流
在数据库中，写入数据的进程负责编码数据，读取数据库的进程负责解码。数据库随时允许更新任何值。如果要更新数据，可以通过数据重写的方式，但是这样的方式对大型数据集来说代价高昂，大多数数据库都会避免，采用类似增加一个默认值为null的新列来解决。
不时为数据制作快照，用于备份或者加载到数据仓库中，数据转储会采用统一的最新编码。

## 流经服务的数据流 REST和RPC
当多个进程需要通过网络通信的时候，可以采用几种不同的组织方式。服务器通过网络公开 API，客户端连接服务器并向 API 发起请求，服务器公开的 API 称为服务。面向服务架构或者微服务架构的关键设计，是让服务可以独立部署和演化，从而使应用更容易修改和维护。

### WEB
用 HTTP 作为服务通信的底层协议，就称为 **web 服务**，web 服务用于构建面向服务或者微服务架构。
最流行的设计理念是 **REST**，建立在 HTTP 的原则上，REST强调简单的数据格式，用 URL 标识资源，利用 HTTP 的功能进行缓存控制，身份认证和内容类型协商。遵循 REST 原则设计的 API 称为 RESTful API。
服务开发者通常使用接口定义语言（IDL）来定义并记录 API 端点和数据模型，随后再逐步演化它们。其他开发者可以根据服务定义判断如何发起请求。最流行的两种服务 IDL 是 OpenAPI（也称为 Swagger）和 gRPC。
即使选定了设计理念和 IDL，开发者仍要编写代码来实现服务的 API 调用。通常可以采用服务框架来简化这项工作。Spring Boot、FastAPI 和 gRPC 等框架让开发者只需编写每个 API 端点的业务逻辑，由框架负责路由、指标、缓存、身份认证等事务。

### RPC
**远程过程调用（remote procedure call，RPC）**，让网络远程请求看起来像函数调用。这种抽象称为位置透明性。这种请求的问题是：
- 网络请求失败的不可预测性，有时请求可能没有到达对端，往往要保证幂等或者重试。数据量很大或者要传输可变对象的时候很麻烦。

### 负载均衡，服务发现和服务网络
所有服务都通过网络通信，客户端必须知道目标服务的地址，这称为**服务发现**。
为了提高可用性和伸缩性，一项服务通常会在不同机器上运行多个实例，把请求分摊到这些实例的过程叫做**负载均衡**。负载均衡有很多实现方案
- **硬件负载均衡器**，安装在数据中心，是安装在数据中心的专用设备。客户端只连接一个主机和端口，设备再把传入连接路由到运行该服务的某台服务器。
- **软件负载均衡器**，安装在客户端或者服务器上，Nginx等。
- **域名系统**DNS，在互联网上解析域名。
- **服务发现**系统，集中注册表追踪哪些端点可用，新服务启动的时候会向发现系统注册自己，之后定期发送心跳，常见的如etcd。
- **服务网格**，更复杂的负载均衡方案，结合软件负载均衡和服务发现。服务网格的负载均衡器则通常部署为进程内客户端库，或者部署为伴随客户端和服务器的进程或“边车”容器。

## 工作流
处理一笔付款需要多次服务调用。支付处理服务可能先调用欺诈检测服务检查风险，再调用信用卡服务扣款，最后调用银行服务把扣下的款项存入账户，这一系列步骤称为 工作流（workflow），其中每一步称为 任务（task）。
工作由工作流引擎运行或者执行，决定每项任务何时运行，在哪台机器运行，失败怎么办，允许多少任务并行。通常由编排器和执行器组成，编排器负责调度，执行器运行任务。

## 持久化
对于需要事务的服务架构，持久化已经成为一种流行的方式。持久化框架可以为工作流提供**恰好一次语义（exactly-once semantics）**。任务失败之后框架会重新执行他，但是跳过之前已经完成的RPC调用或者状态变更，或者返回上一次调用的结果。这是因为框架把所有RPC和状态变更都记录在WAL之类的持久存储中里面。这让代码变更十分脆弱：仅仅调整函数调用顺序，就可能引入未定义行为。与其修改现有工作流的代码，更安全的做法是单独部署一个新版本，让已有工作流的重执行继续使用旧版代码，只有新启动的工作流才使用新版。
持久化执行框架要求以确定性的方式重放所有代码，也就是相同输入必须产生相同输出。因此，随机数生成器、系统时钟等非确定性代码会带来问题。

## 事件驱动框架
**事件驱动架构（event-driven architecture**，这是编码数据在进程间流动的另一种方式。请求在这里称为 事件（event）或 消息（message。发送者通常不会等待接收者处理事件。事件一般也不会通过直接网络连接发给接收者，而是先经过一个临时存储消息的中介，称为 消息代理（message broker），也叫 事件代理（event broker）、消息队列（message queue）或 面向消息的中间件（message-oriented middleware）。
与直接使用RPC相比，有几个优点：
- 接收者不可用或者过载的时候，可以充当缓冲区，提高可用性。
- 自动重传，避免消息丢失
- 不需要服务发现，可以把一条消息发给多个消费者
- 逻辑上解耦了发送者和接收者，消息代理是异步的

### actor
**Actor 模型（actor model**是一种用于单进程并发的编程模型。它不直接处理线程以及随之而来的竞态条件、锁和死锁，而是把逻辑封装在 actor 中。每个 actor 通常代表一个客户端或实体，可以拥有不与其他 actor 共享的本地状态，并通过收发异步消息与其他 actor 通信。消息传递并无保证：在某些错误场景下，消息会丢失。由于每个 actor 一次只处理一条消息，所以无需操心线程问题，而框架可以独立调度每个 actor。
actor 模型本来就假设消息可能丢失，即使消息只在单个进程内传递也一样。网络延迟固然可能高于进程内延迟，但在 actor 模型中，本地通信与远程通信之间的根本差异要小得多。
