Agent 的基础知识，什么是agent？
<!--more-->

# 为什么要有agent
Agent被定义为任何能够通过传感器感知其所处环境，并自主地通过执行器采取行动以达成特定目标的实体。传统的ai工具偏向于“回答用户的问题”，而Agent偏向于“解决用户的问题”。在这个过程中，Agent会 分析问题 → 制定计划 → 执行动作 → 观察反馈 → 继续循环。直到完成问题，普通Ai是一次性响应系统，Agent是持续响应系统。
还有一个AI与Agent的不同是，对于一个比较长期而且比较复杂的任务，Agent的处理能力也比AI更高，因为Ai没有状态，每次调用之间他是失忆的。除非把之前的对话塞进去，但是Agent有记忆和状态。

# Agent的能力
Agent之所以能有这样解决问题的能力，很大程度上是因为三件事情：工具，记忆，推理

## 工具
这是Agent”做事情“的关键，这里的工具不是真正执行（比如调用天气API的地方），而是告诉模型：”你需要什么，我需要返回什么“的说明书。模型是Agent的大脑而不是手脚。只负责决策而不负责执行。
工具通过API，搜索引擎等方式，解放了Agent，让他能够真正为用户做事。

## 记忆
Agent系统通常会设计长期记忆和短期记忆。
- 短期记忆一般是Agent的执行的中间状态，比如上一步的搜索结果是什么，上一步发现的问题是什么。一般存储在上下文里面。
- 长期记忆一般是跨任务的，比如用户的偏好等，存储在向量数据库里面，需要的时候做语义检索拿回来。

## 推理
Agent通过多步推理和自动纠错。Agent的执行如果在某一步失败了，他会分析原因，尝试重试。这种边做边反思的能力，让Agent表现的比自动化的固定流程更好。
上述三种能力结合，让Agent比普通AI更智能，更有能力。如果多Agent协同工作，效果会更好。

# MCP是什么
MCP（Model Context Protocol）是模型上下文协议。是Authropic在2024年提出的工具。在没有MCP之前，每个Agent框架适配工具都要写一套接口。MCP通过定义一套标准的JSON-RPC协议，统一了接口，任何支持MCP的工具都能适应这套代码而不需要自己写接口。
简单来说，MCP解决了——不同Agent怎么调用不同工具的问题，通过三层架构实现：
- Host：用户交互的AI应用
- Client：负责建立连接，管理通信
- Server：提供工具能力和实现

# A2A是什么
MCP解决怎么调用工具的问题，A2A解决Agent间通信的问题。A2A的核心设计是一个Agent Card，类似于Agent的名片，其他Agent只要看到名片就能知道Agent能干什么，正在干什么，需要什么输入

# Agent设计范式
设计范式是什么，可以概括为：Agent怎么组织LLM，Tools，记忆和执行流程。常见的工作范式

## Workflow
Workflow提前把下一步是什么写好，工作流程比较固定。确定性高，好控制。但是灵活性低，遇到没预料到的情况会进入死胡同。

## React
React是 推理（Reasoning）和行动（Acting）交替结合，每一轮React由三个步骤组成 Thought -> Action -> Observation ：思考，行动，观察状态。
为什么要分为这三步呢？如果直接输出行动，模型有时候会搞不懂用户的需求，所以需要思考阶段。而且思考步骤一般是公开可见的，用户可以清楚地看到模型的思路在哪里有偏差。
这个循环会一直反复，直到Agent认为信息已经足够了，可以输出了，Agent才会停下来。
React的明显短板是，他的——走一步看一步的模式，每一步都是局部最优决策。对于一个需要十几步的任务，Agent可能在第五轮就忘了他的最初任务。或者反复重复调用几个工具。

## Plan and Excute
这种工作模式把计划和执行完全分开来，先让一个LLM做决策，给出一个完整计划，然后由另一个LLM（这两个的身份不同）来具体执行。这种结构的好处是复杂任务的步骤非常清楚，用户可以确认计划。
Plan and Excute并不是死板的按照规划执行，而是**动态重规划**，每次执行完都会把结果发给规划器，判断结果是否和预期的一直，后续计划是否需要做出修改。如果某一步结果严重偏离计划，规划器会做出调整。
这种方式的缺点是添加了规划和重规划的LLM调用

## Reflection
这种方法是上面两种方法的基础上加了一层质量保障。再每次LLM执行完调用之后，检查本次执行的质量，做的好不好，是否符合预期。如果评估不通过，就换一种策略。这种情况适用于文案生成等场合。

## Multi-Agent
单Agent会收到上下文大小的限制，对于一个多个分工的任务，单Agent去执行比较不专精。Multi-Agent的思路就是把任务按照职能拆开，而不是让一个Agent包揽所有工作。
Multi-Agent的协作方式主要有三种方式：
- 顺序流水线：A-B-C，像工厂流水线，每个环节依次处理
- 并行扇出：一个调度者把多个独立子任务同时分发给不同的Woker Agent，它们各自并行执行，最后由调度者收集汇总
- 辩论/评审模式：多个Agent对于同一个问题给出方案，然后由一个裁判来给出最优解，或者互相裁判。适合在高质量决策场合使用

目前市面上已经有许多成熟的Agent框架可以使用，另一篇文章会重点介绍这些框架

# Agent推理模式
推理模式的作用是：让 LLM 把隐式的思考过程显式化出来，从而减少多步推理中的累积误差
LLM的工作原理是按照Token一个一个的往后预测，对于一个多步推导的问题，LLM有时候会给出一个“感觉对”的答案，这种答案往往是错的。所以我们需要让LLM把他隐式的思考过程显现出来。

## CoT
Chain of Thought思维链，在Prompt里面加一个「让我们多一步思考」，或者prompt 里给几个带有完整推理过程的例子。前者不太稳定，依赖Agent自由发挥，后者适合输出比较格式的场合，需要提前准备高质量的Token。
CoT是纯文本推理，没办法和外部世界交流

## ToT
Tree of Thoughts（思维树），多路径推理搜索，不是只沿着一条思路往下推，而是同时搜索多条候选思路，评估，然后剪枝。选出最好的路径

##  GoT
GoT全称Graph of Thoughts（思维图），是在ToT基础上的进一步优化，相比较树，允许不同路径的中间结果合并，复用，一个推理节点可以接受多个前置节点的输出作为输入
